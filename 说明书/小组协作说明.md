## 2. 组长首次发布仓库

组长在本地项目目录执行（把 `<仓库地址>` 换成实际地址）：

```powershell
git remote add origin <仓库地址>
git push -u origin main
```

如果推送时提示需要先登录或鉴权，按远程平台的提示完成授权即可。推送成功后，把仓库地址发给组员。

## 3. 组员首次拿到项目

### 3.1 克隆代码

```powershell
cd D:\develop
git clone <仓库地址>
cd smart_pump
```

### 3.2 准备运行环境

需要 Python 3.10+。在项目目录执行：

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install --upgrade pip
.\.venv\Scripts\python.exe -m pip install -r requirements-lock.txt
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
```

也可以直接双击 `一键启动.bat`，脚本会自动准备环境并启动系统。

### 3.3 验证环境

```powershell
.\.venv\Scripts\python.exe -m pytest -q
```

看到全部用例通过即可开始开发。自动化测试使用临时数据库，不会改动本机 `data/pump.db`。

### 3.4 配置提交身份（如本机未配置）

```powershell
git config user.name "你的名字"
git config user.email "你的邮箱"
```

## 4. 日常开发流程

每次开始改代码，按下面四步走：

```text
① 同步 main  →  ② 建自己的分支  →  ③ 修改并提交  →  ④ 推送并申请合并
```

### 4.1 第一步：同步主分支

```powershell
git checkout main
git pull origin main
```

养成习惯：动手前先 pull，避免基于旧代码开发。

### 4.2 第二步：创建自己的分支

分支名用“类型/简短说明”，只用英文小写和连字符：

```powershell
git checkout -b feature/alarm-table
```

| 前缀 | 用途 | 示例 |
| --- | --- | --- |
| `feature/` | 新功能 | `feature/quick-plan` |
| `fix/` | 修缺陷 | `fix/chart-duplicate-id` |
| `docs/` | 文档修改 | `docs/user-manual` |
| `refactor/` | 代码整理 | `refactor/ui-style` |

每人一次只在一个分支上做一件事，做完就合并，避免分支越积越多。

### 4.3 第三步：修改、测试、提交

```powershell
git status
.\.venv\Scripts\python.exe -m pytest -q
git add .
git commit -m "feat: 优化页新增一键方案卡片"
```

提交信息统一格式：`类型: 简短说明`

| 类型 | 含义 |
| --- | --- |
| `feat` | 新功能 |
| `fix` | 修复问题 |
| `docs` | 文档 |
| `test` | 测试 |
| `refactor` | 重构或样式调整 |

要求：**一次提交只做一件事**，提交前必须跑测试，不要提交跑不通的代码。

### 4.4 第四步：推送并申请合并

```powershell
git push -u origin feature/alarm-table
```

然后到远程仓库网页上创建 Pull Request / Merge Request，说明本次改了什么，请其他组员简单 review 后合并到 `main`。合并后删除该分支：

```powershell
git checkout main
git pull origin main
git branch -d feature/alarm-table
```

## 5. 冲突处理

多人改到同一个文件时可能产生冲突。处理原则：

1. **先沟通**：确认两人的改动是否都要保留，不要自行覆盖别人的代码。
2. **拉最新代码**：在冲突分支上执行 `git pull origin main`，Git 会标出冲突文件。
3. **手动解决**：打开冲突文件，找到 `<<<<<<<`、`=======`、`>>>>>>>` 标记，保留需要的内容，删掉标记。
4. **完成合并**：
   ```powershell
   git add .
   git commit -m "fix: 合并 main 并解决冲突"
   git push
   ```

容易冲突的文件：`utils/ui.py`（样式）、`pages/*.py`（页面）、文档 `.md`。建议同一文件尽量由一人负责，或提前在群里说一声。

## 6. 项目文件约定

### 6.1 不要提交的文件

以下已写入 `.gitignore`，**不要**用 `git add -f` 强行提交：

| 文件/目录 | 原因 |
| --- | --- |
| `.venv/`、`.venv313/` | 虚拟环境，体积大且各机不同 |
| `data/pump.db` | 本机演示数据，含个人操作痕迹 |
| `artifacts/`、`dist/` | 过程产物与交付压缩包 |
| `runtime/`、`backups/` | 本机运行与备份文件 |
| `.workbuddy/` | 工作区本地数据 |

`data/.gitkeep` 需要保留，用来维持 `data/` 目录结构；数据库会在首次启动时自动创建。

### 6.2 文档要成对更新

Word 文档由 Markdown 生成。改完 `.md` 后同步生成 `.docx`（项目环境已装 pandoc）：

```powershell
pandoc 智能抽油机系统使用说明书.md -o 智能抽油机系统使用说明书.docx --from=gfm --to=docx
```

### 6.3 改代码时的注意点

- 改诊断阈值、冲次范围等参数时，统一改 `core/config.py`，不要在页面里写死数字。
- 新增页面要放进 `pages/` 并在 `app.py` 的 `st.navigation` 中注册。
- 同一页面出现多个相同配置的图表时，要给 `st.plotly_chart` 传不同的 `key`，否则会报重复元素 ID 错误。
- 新增功能后同步更新说明书和 README，避免文档与实现不一致。

| 文档齐全 | 使用说明书、需求分析、技术方案、测试报告均为最新版 |

## 8. 常用命令速查

```powershell
git status                          # 查看改动
git pull origin main                # 拉取最新主分支
git checkout -b feature/xxx         # 新建分支
git add .                           # 暂存全部改动
git commit -m "feat: 说明"          # 提交
git push -u origin feature/xxx      # 推送分支
git log --oneline --graph           # 查看提交历史
git diff                            # 查看未暂存的改动
git checkout main                   # 切回主分支
```

> **记住三件事：动手前先 pull，提交前先跑测试，永远不在 main 上直接写代码。**
